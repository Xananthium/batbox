The existing plugin Triton implementation dequantizes and performs a separate `tl.dot` per32-value Q4_K group or16-value Q6_K group. It casts parent scales to the activation dtype before arithmetic. The candidate `direct_gemm.py` instead decodes an entire K128/K256 tile, reconstructs scale/minimum in FP32, and then performs the Tensor Core dot. It reads original GGUF bytes directly and does not grow the persistent weight allocation. It uses the standard tiled Triton approach, while the longer-term mature implementation to reuse is current llama.cpp's Ampere MMQ.

Current llama.cpp has explicit Q4_K and Q6_K **MMA** dispatch, architecture-specific Ampere tile configurations and Stream-K scheduling. This is not the b2899 DP4A path in the installed plugin. The quantization constraints are precise:

| Format | Original represented weight | Original block storage | Lossless metadata-expanded prototype |
|---|---|---:|---:|
| Q4_K | `(FP32(d) × scale6) × code4 − FP32(dmin) × min6`, groups32 |144bytes/256 =4.5bits/weight|4-bit codes + two FP32 parameters/group32 =6bits/weight|
| Q6_K | `(FP32(d) × signed_scale8) × (code6−32)`, groups16 |210bytes/256 =6.5625bits/weight|6-bit codes + one FP32 parameter/group16 =8bits/weight|

Q4_K retains two half superblock parameters plus eight6-bit scale/min pairs. Q6_K retains a half superblock parameter plus sixteen signed8-bit scales. Computing those group parameters in FP32 is exact for their integer/half products. Keeping the separate scale and minimum avoids a rounded division through a floating zero point. Q6_K's group16 must not silently become group32. Stock vLLM Marlin accepts group sizes `[-1,32,64,128]`; a group16 decoder/kernel extension or a different kernel is needed. Neither limitation requires changing the original integer codes. [GGML format definitions](https://github.com/ggml-org/llama.cpp/blob/36e36e63a54fc8f85b95e9c499a022b597e478dd/ggml/src/ggml-common.h), [vLLM Marlin constraints](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/quantization/utils/marlin_utils.py), [Marlin kernel design](https://github.com/IST-DASLab/marlin).

For this entire source checkpoint, the metadata-expanded repack would grow quantized tensor storage from18,665,902,080bytes to24,378,998,784bytes (+30.61%, before other tensors). It is a fidelity/layout demonstration, not a proposal to duplicate both formats on GPU. The direct candidate uses the original allocation and only per-tile registers/shared memory.

The tests completed without GPU use:

- `verify_cpu.py`:27,392,000 sampled real values across **all411 quantized tensors**, plus4,194,304 synthetic values including signed scales, zero/subnormal/extreme finite half parameters and random code bit patterns. The independent installed GGUF decoder, repacked decoder and direct-offset decoder have **zero FP32 bit mismatches and zero integer-code mismatches**. These are samples of every tensor, not an exhaustive scan of every checkpoint value.
- `verify_kernel_cpu.py`: the actual Triton address/masking code executed under its CPU interpreter in IEEE mode. Six Q4_K/Q6_K cases cover odd M/N, multiple superblocks, K128/K256 tiles and strided X/W. Relative RMS versus CPU FP64 reference is below1.7e-7. This validates the interpreter path, not CUDA code generation.
- `compile_cpu.py`: all six Q4_K/Q6_K × BF16/BF16-pair/TF32x3 variants compiled offline toSM86; emitted PTX contains `mma.sync` BF16 or TF32 instructions. This proves compilation and instruction selection, not GPU correctness or speed.

`direct_gemm.py` exposes three precision choices. `bf16` rounds each fully reconstructed FP32 weight once before the dot. `bf16_pair` represents that weight with a BF16 high value plus BF16 residual and uses two dots; on the real sampled weights its maximum representation relative RMS is1.91e-6, compared with1.69e-3 for one BF16 value. `tf32x3` supplies reconstructed FP32 weights to Triton's multi-pass Tensor Core mode. None is advertised as bitwise equivalent to the original A8 activation path or an exact FP64 matmul. All return BF16 outputs, so final output rounding remains. [Triton dot precision contract](https://triton-lang.org/main/python-api/generated/triton.language.dot.html).

The separate `audit_saved_affine.py` uses the **actual saved** native INT4 tensors at the same sampled rows as the existing conversion audit. The export receipt evaluates `(signed_code−BF16(zp))×BF16(scale)` in FP32. The installed runtime additionally rounds `−zp×scale` toBF16 before applying its separate correction. Across18 matrices and5,592,832 sampled values,166,953 of174,776 group offsets change. The maximum additional coefficient relative RMS versus the receipt is0.000639; maximum source-relative RMS moves from0.004034 to0.004080. This audit excludes Marlin's multiplication rounding, grouped activation sums, correction GEMM and final add. Thus it establishes a missing rounding stage in the receipt, not the total runtime error. Artifacts: `saved-affine-results.json` and `cpu-results.json`.
